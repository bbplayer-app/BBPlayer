# 后台播放功耗测量

`measure-background-power.sh` 的用法见脚本开头的注释。这里是测量的标准操作流程：整机电流很容易被其他 app、蓝牙、蜂窝网络干扰，不按流程测出来的数据基本没法互相比较。

## 原则

- **只比较同一台手机上、前后挨着测的数据。** 不同日期、不同电量、不同环境下的电流不能直接比。
- **一次只改一个变量。** 比如只换 app 版本，或只切换频谱开关，其余条件全部不变。
- **交替测量，至少重复一轮。** 按 A → B → A → B 的顺序测，两次 A 的差距就是这一组数据的噪声水平。B 和 A 的差距明显超过这个噪声，才算有效。
- **优先看 CPU 和唤醒，电流作为辅助。** 进程/线程的 CPU 时间和唤醒次数几乎不受背景干扰。整机电流会把其他 app 和无线模块也算进去。

## 测量前

`start --normalize` 会自动完成下面「无线模块」的离线方案、把媒体音量设为 0、清理后台进程，并在 `collect` 时恢复原来的设置；电量、温度、省电模式、倍速不对时会给出警告。其余几项仍需手动确认。

### 手机状态

1. 电量在 50%～90% 之间，几次测量的起始电量相差不超过 10%。电量越高电压越高，同样的功耗电流会更低，满电附近还可能涓流充电。
2. 手机不烫：报告里的起始温度不要高于 32°C。刚充完电或刚玩过游戏，先放 10 分钟。
3. 省电模式、自动亮度、刷新率等系统设置在几次测量之间保持一致。
4. 清空后台的其他 app。

### 无线模块

按测量目的选一种，几次测量之间不要混用：

- **只看 app 自身开销（推荐）：** 歌单提前完整缓存，然后开飞行模式，再确认 Wi-Fi 和蓝牙都是关的。这样能排除蜂窝网络、其他 app 推送、蓝牙扫描带来的干扰。
- **模拟真实使用：** 网络照常，但蓝牙要么全程关闭，要么全程连着同一副耳机。不要处于"开着但没连接"的状态，这时系统会一直扫描，每分钟唤醒几十次。

### 音频

1. 输出设备固定为外放，媒体音量固定，推荐调到 0，可以排除功放的功耗。
2. 关闭系统音效（三星：杜比全景声、自适应音效等），否则可能无法 offload。
3. 倍速 1x。频谱开关按本次要测的变量设置。
4. 播放同一个已完整缓存的歌单，顺序播放，从同一首开始。不要单曲循环，那样测不到换歌的开销。

### App

1. 杀掉 app 再冷启动，开始播放。
2. 播放约 1 分钟后再执行 `start`，跳过启动阶段。
3. 需要确认音频通路时，打开 设置 → 开发者 → 音频调试，看输出模式（offload / PCM）和 AudioTrack 缓冲大小。

## 测量

```bash
ANDROID_SERIAL=<序列号> ./scripts/power/measure-background-power.sh start -m 10 --normalize
```

1. `start` 之后拔掉 USB。采样器会一直等到拔线，再预热 2 分钟（`-w` 调整）才开始计时，电池统计也在这时才清零，所以不用急着拔，插线和预热阶段都不会算进测量。
2. 脚本会自动回到桌面并熄屏。测量期间不要碰手机，放在固定位置，不要移动。
3. 时长 10 分钟。少于 8 分钟时，电量计数器只走几 mAh，误差占比太大。
4. 拔线 13 分钟（预热加测量时长）之后插回 USB，执行 `collect`。用了 `--normalize` 的话会顺带恢复飞行模式、Wi-Fi、蓝牙和音量；如果中途放弃了这次测量，用 `restore` 手动恢复。

## 记录

采样器会在开始和结束时各记录一次测试条件（无线模块、省电模式、媒体音量、后台进程数、播放状态、AudioFlinger 里的音频通路和缓冲大小），报告第 0 节列出这些条件，并指出会影响可比性的地方。

脚本记录不了的，在结果目录里新建一个 `notes.md` 手动记下：

- 测的是哪个版本、什么变量（如"PCM 缓冲 2s，频谱开"）
- 测量期间有没有收到电话、通知，或被意外亮屏

## 看报告

- 不看最后一分钟（可能已经插线、亮屏）。有了拔线后的预热，第 0 分钟一般可以正常看；用 `-w 0` 关掉预热时，第 0 分钟也不要看。
- 电流看「电池 HAL 实时计数」的中位数，以及每分钟平均值的中位数。平均值容易被个别尖峰拉高。
- 对比时先看第 0 节：条件不一致，或者无线模块的内核唤醒锁（蓝牙、蜂窝网络）在两组之间差距很大，电流就不能直接比。`system_server` 的 CPU 差距很大也说明背景不同。
- 电流差距在 15% 以内的，没有重复测过就当作噪声。
